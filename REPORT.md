# Звіт про виконання лабораторної роботи №2
## «Класи, record і інкапсуляція в Java-проєкті»

### 1. Тема, номер і варіант
- **Дисципліна:** «Кросплатформні засоби програмування»
- **Лабораторна робота №2:** «Класи, record і інкапсуляція в Java-проєкті»
- **Номер варіанта:** 10
- **Предметна область:** Магазин техніки
- **Мова та інструментарій:** Java 21, Apache Maven (Maven Wrapper, Surefire, SpotBugs, Resources filtering, Shade), JUnit 5, GitHub Actions
- **Операційна система розробки та перевірки:** Windows (локально); Ubuntu, Windows та macOS (у GitHub Actions CI)

### 2. Мета роботи
Метою роботи було перебудувати предметну частину консольного застосунку з лабораторної роботи №1 для варіанта №10 («Магазин техніки»), замінивши рядкове представлення записів і паралельні/локальні змінні обробки на об'єктно-орієнтовану модель з інкапсуляцією, перевіркою інваріантів, незмінними `record`-типами, розподілом відповідальностей (`Main` / `CliParser` / `StoreController`), автоматичним підтягуванням версії з `pom.xml` та модульними тестами JUnit 5 зі збереженням зовнішньої поведінки та звіту.

### 3. Стан до і після цієї роботи
До виконання лабораторної роботи №2 розбір CSV-рядків, перевірка коректності полів і підрахунок статистики виконувалися без виділеного класу предметної сутності та допоміжних `record`-структур, а версія проєкту могла фіксуватися поза єдиним джерелом або потребувала додаткового впорядкування точки входу.

Після перебудови у гілці `lab2-classes`:
- Рядковий запис товару з полями `name`, `category`, `price`, `warrantyMonths`, `stock` замінено незмінним класом-сутністю `Product` (`private final` поля, перевірка інваріантів у конструкторі, фабричний метод `fromCsv`, геттери, форматований `toString` із `Locale.ROOT`).
- Пару параметрів гарантії та складського залишку винесено у незмінний `record` `WarrantyStock(int warrantyMonths, int stock)` із валідацією невід'ємних значень.
- Підсумкові показники обробки винесено у незмінний `record` `StoreSummary(int validCount, double averagePrice, int maxWarranty, int totalStock)`.
- Розбір аргументів командного рядка винесено у `CliParser` та `CliOptions`, координацію читання, валідації, статистики і запису звіту — у `StoreController`, а `Main` залишено легкою точкою входу.
- Версія застосунку підтягується автоматично з `<version>` у `pom.xml` через фільтрацію ресурсів (`app.properties` + `BuildInfo`) без жорстко зашитих констант версії в Java-класах.

### 4. Клас-сутність
Клас `ua.lpnu.kzp.Product` оголошено як `public final class` і реалізує сутність варіанта №10 («Магазин техніки»):
- **Поля:** `private final String name`, `private final String category`, `private final double price`, `private final WarrantyStock warrantyStock`. Публічних сеттерів немає, що захищає стан об'єкта після створення від неконтрольованих змін.
- **Інваріанти у конструкторі:**
  - `name` і `category` не можуть бути `null` (`Objects.requireNonNull`) та не можуть бути порожніми або складатися лише з пробільних символів (`isBlank()`).
  - `price` має бути скінченним невід'ємним числом (`price >= 0 && Double.isFinite(price)`), що відхиляє від'ємні ціни, `NaN` та нескінченність.
  - `warrantyMonths` і `stock` делегуються у `WarrantyStock` і не можуть бути від'ємними (`>= 0`), при цьому нульові граничні значення дозволені.
- **Методи читання та `toString()`:** реалізовано `getName()`, `getCategory()`, `getPrice()`, `getWarrantyMonths()`, `getStock()`, `getWarrantyStock()`, а також перевизначено `toString()` із використанням `Locale.ROOT` для стабільного форматування дробових чисел незалежно від регіональних налаштувань ОС.

### 5. Фабричний метод і record
- **Фабричний метод `Product.fromCsv(String line)`:** перевіряє рядок на `null`, розбиває за роздільником `;` (`split(";", -1)`), контролює кількість полів (очікується 5 полів), виконує обрізання пробілів (`trim()`) і числове парсинг-перетворення (`Double.parseDouble`, `Integer.parseInt`), після чого передає значення у конструктор `Product`. Помилки формату чисел перехоплюються і загортаються в `IllegalArgumentException`, а у `StoreController` кожна помилка фіксується із зазначенням номера рядка (`Рядок N: ...`).
- **Допоміжні `record`:**
  - `WarrantyStock` — компактний незмінний носій гарантії в місяцях і запасу на складі з перевіркою невід'ємності у компактному конструкторі.
  - `StoreSummary` — незмінний підсумковий результат обробки (`validCount`, `averagePrice`, `maxWarranty`, `totalStock`), що усуває потребу передавати кілька розрізнених змінних між методами.

### 6. Тестування
У пакеті `src/test/java/ua/lpnu/kzp/` збережено попередні тести та додано нові тести JUnit 5 (`Lab02ModelTest`), які перевіряють:
- **Позитивні випадки:** коректне створення `Product` та `fromCsv`, роботу геттерів, `toString()` з крапковим десятковим роздільником через `Locale.ROOT`, розбір аргументів у `CliParser`, обчислення `StoreSummary` та формування звіту у `StoreController`.
- **Граничні випадки:** нульові значення ціни (`0.0`), гарантії (`0`) та залишку на складі (`0`), порожній список коректних записів.
- **Негативні випадки:** `null` і порожні/пробільні рядки для назви й категорії, від'ємні значення ціни/гарантії/залишку, `Double.NaN` та `Double.POSITIVE_INFINITY`, неправильну кількість полів у CSV, нечислові значення та невідомі/неповні параметри CLI.

### 7. Інфраструктура
Успадкована конфігурація Maven і GitHub Actions збережена та перевірена:
- Виконано локальні перевірки `.\mvnw.cmd clean verify` та `.\mvnw.cmd clean verify package` (успішна компіляція під Java 21, проходження тестів JUnit 5, перевірка статичного аналізу SpotBugs та створення виконуваного shaded JAR).
- Перевірено запуск JAR-артефакту (`--version`, `--input`, `--output`).
- У Pull Request запущено GitHub Actions на трьох операційних системах (`ubuntu-latest`, `windows-latest`, `macos-latest`) та підготовлено оновлення версії і Git-тегу.

### 9. Порівняння поведінки
Для перевірки відсутності регресій використано контрольний вхідний файл `data/input.csv` та порівняно результати до і після перебудови:
- Кількість коректних записів, середня ціна, найдовша гарантія, загальна кількість товарів на складі та кількість помилок залишилися ідентичними.
- Номери рядків із помилками та текст звіту збережено у сумісному вигляді.
- У консолі Windows при запуску JAR через `java -jar` у середовищі без увімкненого UTF-8 (`[Console]::OutputEncoding`) у виводі термінала можуть з'являтися `?` або `╨...`, тоді як вихідний файл звіту (`out/report.txt`) записується у кодуванні `UTF-8`.

### 11. Відповіді на контрольні питання
1. **Клас-сутність vs рядки і змінні:** об'єднує дані та правила їх коректності в одному типі замість розкиданих індексів, масивів і окремих змінних.
2. **`private` і `final` у полях:** `private` забороняє прямий доступ ззовні класу, а `final` гарантує, що посилання або значення поля не буде переприсвоєно після завершення конструктора.
3. **Інкапсуляція:** приховування внутрішнього стану об'єкта та надання контрольованого інтерфейсу, що запобігає псуванню даних і порушенню правил предметної області.
4. **Перевірка інваріантів у конструкторі:** не дозволяє створити і повернути об'єкт у невалідному стані.
5. **`Objects.requireNonNull` vs `isBlank()`:** перше перевіряє наявність посилання (`null`), а друге — чи рядок порожній або містить лише пробільні символи.
6. **Відсутність сеттерів:** не дає змінити поля об'єкта в обхід валідації після його створення.
7. **Методи й властивості `record`:** компілятор генерує канонічний конструктор, методи доступу за назвами компонентів, `equals`, `hashCode` та `toString`.
8. **`record` vs звичайний клас-сутність:** `record` призначений для компактних незмінних носіїв даних із автогенерацією шаблонних методів, тоді як звичайний клас зручніший для складнішої доменної поведінки та гнучкої інкапсуляції.
9. **Чому `record` не гарантує глибоку незмінність змінного списку:** незмінним є саме посилання на список у компоненті `record`, а не внутрішній стан самого змінного об'єкта списку.
10. **Призначення `fromCsv`:** інкапсулює розбір текстового рядка CSV та перетворення типів перед створенням об'єкта через конструктор.
11. **Перехоплення помилки рядка:** у циклі читання навколо виклику `fromCsv`, щоб помилка одного некоректного рядка не переривала обробку всього файлу.
12. **Чому хибний запис не додається до списку:** щоб не забруднювати колекцію валідних об'єктів і не спотворювати підсумкову статистику.
13. **Призначення `toString` і чому не замінює CSV:** `toString` дає зручне текстове подання об'єкта для логів/виводу, а CSV — це структурований формат обміну даними з чіткими полями й роздільниками.
14. **`Locale.ROOT` у `toString` і звіті:** забезпечує стабільне форматування чисел (зокрема крапку як десятковий роздільник) незалежно від локалі системи.
15. **Схема ААА (Arrange – Act – Assert):** підготовка даних і стану, виконання цільової дії, перевірка очікуваного результату.
16. **Негативні випадки для конструктора:** `null` або порожні/пробільні рядки, від'ємні числа, `NaN` і нескінченність для дробових полів, порушення предметних обмежень.
17. **Доказ збереження поведінки:** запуск на тому самому вхідному файлі та порівняння метрик, списку помилок і тексту звіту з результатом попередньої роботи.
18. **Проходження попередніх тестів:** гарантує, що рефакторинг не зламав наявну функціональність і сумісність.
19. **Успадкована інфраструктура:** Maven Wrapper (`mvnw`, `mvnw.cmd`), `pom.xml`, конфігурація тестів/аналізатора/пакування та workflow GitHub Actions.
20. **Демонстрація інкапсуляції:** `private final` поля у `Product` у поєднанні з перевіркою інваріантів у конструкторі та відсутністю сеттерів гарантують, що кожен створений екземпляр `Product` завжди перебуває у коректному стані.

### 12. Висновки
У результаті лабораторної роботи №2 предметну область «Магазин техніки» (Варіант 10) переведено на об'єктно-орієнтовану модель із класом `Product`, незмінними `record`-типами `WarrantyStock` і `StoreSummary`, розділенням логіки між `Main`, `CliParser` та `StoreController`, автоматичним підтягуванням версії з `pom.xml` і покриттям тестами JUnit 5 зі збереженням зовнішньої поведінки та звіту. Сформована об'єктна модель стане основою для лабораторної роботи №3, де сутності та обробка будуть розвиватися далі (зокрема через ієрархію типів і поліморфну роботу).
